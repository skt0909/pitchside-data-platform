    What is on this site

    Architecture

    App to Marketplace

    Data moves in one direction, one hop at a time. dbt and the marketplace run off the VM.

    Data Flow

    From the app's database, through three quality gates, to the people and tools that use it. The Gold layer holds the tables and the semantic layer together.

    Gold is two things

    The Gold tables hold the numbers. The semantic layer sits on top of them and holds the definitions, so a metric such as points per 90 minutes is calculated the same way for everyone.

    Both live in dbt

    Tables are built from models/marts/*.sql. The semantic layer is _semantic.yml in the same folder: 4 semantic models and 6 metrics, queried with mf query.

    What the product promises

    The data product contract names four Gold tables and six metrics, with their types, tests, limits and freshness. It is documentation and a promise to consumers.

    The 3 gates

    1. The load. Row counts must match the batch manifest before Bronze is replaced. A mismatch stops the load.
    2. The source. Freshness on _loaded_at warns after 36 hours and errors after 72.
    3. The build. dbt tests and enforced contracts must pass before Gold is trusted.

    The layers

    • lake: dated Parquet and a manifest per batch, kept as history.
    • bronze: a faithful copy, replaced each load, numbers stored as text.
    • silver: ten views that rename and cast, no business rules.
    • gold: seven tables plus the semantic layer on top.

    Around it

    • sources: one Postgres database, fed by the app from the football API.
    • metadata: the data product contract, the dbt manifest and the lineage links.
    • ops: batch manifests, dbt run results and, once scheduled, a status file per run.
    • dashed lines: planned, not running yet.

    Security model

    Database access

    • Dedicated role. extract_role can log in, with at most 2 connections, and read only the 10 approved tables.
    • Heartbeats. On task_heartbeats it can read three columns only.
    • Checked. Reading users and last_error is denied.
    • No reuse. It shares nothing with the existing existing_readonly_role role.

    Cloud access and exclusions

    • No key files. The VM acts as the extractor-service-account service account by impersonation.
    • Never extracted. users, password reset tokens, invite codes, the last_error column, alembic_version and all user-linked tables.
    • Not in git. Passwords and tokens stay on the VM.
